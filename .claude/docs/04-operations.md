## PRODUCTION: the b4l box (this machine) — live since 2026-08-05

This machine **is** a production connector host. `digi-erp-connectord` replaced
the electron-mssql-app connector here on 2026-08-05 16:35.

- **Serves `[::]:8082`** (dual-stack, all interfaces) because a remote backend
  calls it over the LAN. Firewall rule "Digitrade" (inbound TCP 8081+8082,
  `Program: Any`) already allows it — it is not tied to any executable.
  Do NOT "harden" this back to 127.0.0.1: it would cut off the backend.
- DB: `localhost:1433/BFL`, user `sa`, `encrypt: true` +
  `trustServerCertificate: true` (local self-signed cert — both are required,
  they mirror the old app's connection settings).
- **Auth status (2026-08-09, read this before deploying anything here).** Three
  changes landed the same day, in this order: the legacy compatibility layer was
  deleted; erp-manager declined the static-token migration, so `/auth/token` and
  `/api/ping` came back as a first-class `auth:` block with per-install
  credentials (v1.0.13); then the static `bearerToken` was removed entirely, at
  the operator's instruction, leaving username+password → `/auth/token` as the
  only scheme (v1.0.16). `/api/query` and the sample routes stayed deleted
  throughout.

  Which release does what, because they are not interchangeable:

  | Release | Auth |
  |---|---|
  | ≤ 1.0.4 | `/auth/token` with the shipped `digitrade`/`123456` |
  | 1.0.5 – 1.0.10 | **no `/auth/token` at all** — breaks BFL outright, never install |
  | 1.0.13 – 1.0.15 | `/auth/token` with per-install credentials, static token still accepted |
  | 1.0.16+ | `/auth/token` only — no static token anywhere |

  Deploying 1.0.16 needs the box's `auth:` credentials to already match
  `authLogin`/`authPassword` on ClientConnection rows 67 (`:8082`) and 76
  (`:8083`, BFL-SendOrders). Keeping `digitrade`/`123456` in the `auth:` block
  makes the upgrade transparent to erp-manager; rotating them is a separate step
  that needs the backend updated first.
  Background: `docs/connector-adaptation-plan.md`, `docs/authentication.md`,
  decisions 15–17.
- `queries.maxRows: 100000`, not the 10000 default: the `IndividualProductList`
  saved query legitimately returns 16183 rows and the old connector had no cap.
  Lowering it back to 10000 will make that query fail with 413.
- Service runs as LocalSystem, `depend= MSSQL$WIZSOFT2017`, with failure
  recovery `restart/15s, 30s, 60s` (reset daily). Both were added at cutover,
  when the daemon still aborted if the DB was unreachable at startup. That is no
  longer true (2026-08-06: `db.OpenLazy` — it starts, warns, and serves 503 until
  the database answers), so these settings are now belt-and-braces rather than
  load-bearing. Keep them: they order the service starts sensibly and restart the
  connector if it exits for any other reason.
- The electron app was **uninstalled** on 2026-08-05 after the connector ran
  clean, and no installer for it exists on this box. It is therefore no longer a
  rollback path; its config and all 25 saved queries are preserved under
  `cutover-backup-2026-08-05\`. Rolling back to it would mean sourcing the old
  installer from whoever built it.

### Installing a new release over a running install

The installer does NOT stop the service (`[Run]` only does `sc create` /
`sc start`), so **stop the service first** or the running exe cannot be replaced.
`sc create` fails harmlessly on an existing service, which means the service
definition — including `depend=` and the recovery actions — **survives** an
upgrade install. Re-running the hardening afterwards is still worth it as a
cheap idempotent check; `install-1.0.4-and-harden.ps1` does the whole sequence
with auto-rollback.

Only `[UninstallRun]` stops and deletes the service, so a full uninstall does
lose the hardening.

### Verifying the box

```powershell
# who serves 8082
Get-NetTCPConnection -State Listen | Where-Object LocalPort -eq 8082
# get a token, then use it (JSON bodies must go through a file: PowerShell 5.1
# strips double quotes when passing strings to native exes)
# on 1.0.4 the credentials are digitrade/123456; from 1.0.16 they are whatever
# this box was provisioned with, and there is no other way to authenticate.
'{"username":"digitrade","password":"123456"}' | Set-Content "$env:TEMP\b.json" -Encoding ascii -NoNewline
curl.exe -s -X POST http://127.0.0.1:8082/auth/token -H 'Content-Type: application/json' --data-binary "@$env:TEMP\b.json"
curl.exe -s http://127.0.0.1:8082/api/ping   -H "Authorization: Bearer <access_token>"   # no DB touch
curl.exe -s http://127.0.0.1:8082/api/health -H "Authorization: Bearer <access_token>"   # pings the DB
# who is failing to authenticate, and with which username
Select-String -Path C:\ProgramData\digi-erp-connector\server.log -Pattern 'rejected /auth/token'
```

# Security model

What the connector defends, how, and where it deliberately does not. This
describes the code as it is — not aspirations.

## Threat model

The connector is a small HTTP service that holds credentials for, and arbitrary
SQL access to, a customer's ERP database. It runs as LocalSystem.

Assume:

- **Anything that can reach the port and holds the bearer token can run the stored
  SQL.** Saved queries are trusted by design and may contain writes.
- **The machine's administrators are trusted.** `config.yaml` is 0600 with the
  token in plaintext, and the DB password uses DPAPI *machine* scope, so any
  process on the machine can decrypt it. That is required — the LocalSystem
  service must read what the GUI wrote.
- **The network may not be.** If `apiListen` is not loopback, the bearer token is
  the only barrier in front of the database.

Out of scope: a hostile local administrator, physical access, and SQL Server's own
hardening.

## Authentication

Every `/api/*` route requires `Authorization: Bearer <token>`, compared against
`config.bearerToken` with `crypto/subtle.ConstantTimeCompare`. Failure is a flat
`401 UNAUTHORIZED` — no distinction between "missing" and "wrong", and the token is
never logged.

The token is generated by the GUI as 32 random bytes from `crypto/rand`, hex
encoded. Treat it as a database credential, because that is effectively what it is.

**Rate limiting runs before authentication** — a per-IP token bucket (25 rps,
burst 50) returning `429 RATE_LIMITED`. So an unauthenticated flood is shed
cheaply, and token guessing is throttled. Buckets are capped at 4096 with
10-minute idle eviction, so spoofed source IPs cannot exhaust memory.

There is no user model, no roles, no token rotation and no expiry. One
installation, one credential. If short-lived tokens are ever needed, add an
exchange endpoint rather than reviving the hardcoded-credentials flow that the
legacy connector used.

## SQL access

There is **no raw-SQL endpoint by default**. The backend cannot send SQL text; it
registers queries by name through CRUD and executes them by name.

What that buys: the attack surface is the *set of registered queries*, not
arbitrary SQL, and every request value is bound with `sql.Named()` — never
concatenated. Injection through parameters is not possible.

What it does not buy: saved queries are **trusted** and may contain `INSERT`,
`UPDATE` or `EXEC`. Whoever holds the token can register a destructive query and
run it. The boundary is the token plus the CRUD store, not a keyword filter — a
deliberate decision inherited from the connector this replaced. Mitigate with a
least-privilege SQL login: grant only what the customer's queries actually need.

Execution is bounded — `queries.timeoutSeconds` (default 30) and `queries.maxRows`
(default 10,000) — so one query cannot hold a connection or exhaust memory
indefinitely.

**The documented exception:** `POST /api/query` accepts SQL text, exists only when
`legacyCompat.allowRawSQL` is true, and is validated read-only (single statement,
`SELECT`/`WITH` only, no comments, keyword blocklist applied after string literals
are stripped), fully parameter-bound, and logged in full on every call. See
[legacy-compat.md](legacy-compat.md). Do not add a second one.

## File access

`POST /api/file` and `GET /api/folders/list` serve only from `imageFolders`.
`ResolveFilePath` (`internal/files`):

1. canonicalises the requested folder (absolute, cleaned, symlinks resolved) and
   requires an **exact** match against a configured folder — case-insensitively on
   Windows
2. rejects a `fileName` that is `.`, `..` or absolute
3. joins and re-checks containment with `filepath.Rel`
4. resolves symlinks on the final path and **re-checks containment**, so a symlink
   inside an allowed folder cannot point out of it

Subfolders are not reachable unless listed. Failures return
`400 INVALID_FILE_PATH` without revealing whether the path exists. Tests cover
traversal, allow-list enforcement, and that a folder supplied in a non-canonical
form (short 8.3 path, junction) still matches.

## Secrets at rest

| Secret | Where | Protection |
|---|---|---|
| DB password | `secrets/db_password_<erp>.bin` | Windows DPAPI, machine scope. **Plaintext on Unix** — the daemon supports Linux but its secret storage does not protect anything there. |
| Bearer token | `config.yaml` | File mode 0600 only. |

Both files are written atomically. Writes report failure — a secret write that
silently "succeeded" while failing used to leave the daemon starting with the wrong
password and no explanation.

Neither value is ever logged. Log lines about the password mention only its length.

## What is logged

Method, path, status, duration, and enough startup detail to diagnose a failed
start (config summary, DB host/port/user/database, query count). Legacy-compat
route hits are logged by design, including the full SQL text of any
`POST /api/query` — that is the audit trail for the one route that accepts SQL.

Never logged: the bearer token, the DB password, JWT contents.

Driver errors are logged but **never returned to callers**: a DB error message can
name schemas, hosts and logins, so clients get a generic message plus a stable
code.

## Network exposure

Default `apiListen` is `127.0.0.1:8080` — loopback. Keep it there unless the
backend genuinely runs elsewhere.

If you must expose it: the token is the only barrier, so restrict the firewall rule
to the backend's source address if it is stable, prefer a port-scoped rule over a
program-scoped one (a replaced binary silently loses a program rule), and treat the
token like a password — rotate it by editing `config.yaml` and restarting.

There is no TLS. Traffic is plaintext HTTP, so on an untrusted network put it
behind something that terminates TLS, or keep it on loopback.

## Least-privilege database user

The connector needs:

- `SELECT` on whatever the customer's saved queries read
- write permissions only if their queries write
- `EXECUTE` on `GPRICE_Bulk` / `GetOnHandStockForSkus` for Hasavshevet price/stock
- `CREATE`/`ALTER` **once**, if you want the GUI to install those procedures (or
  pre-create them and revoke — they then will not be updated on upgrade)
- read on the accounts/rates tables the order pipeline queries

Granting `sysadmin` is common in the field and is not necessary.

## Known limitations

- No TLS, no token expiry, no per-route authorisation.
- Secrets are not protected at rest on Linux.
- Saved queries are unrestricted by design.
- `POST /api/query` is a read-only-validated exception that exists for migration
  and should be retired — [legacy-compat.md](legacy-compat.md) says how.
- The compatibility layer's JWT credentials live in `config.yaml` in plaintext when
  enabled. That is why it defaults to off and carries no credentials in the binary.

# Authentication

The connector accepts **two credentials**, and both authenticate every `/api/*`
route identically:

| Credential | Configured as | Obtained by the caller |
|---|---|---|
| Static bearer token | `bearerToken` | copied from `config.yaml` once, used forever |
| Issued token | the `auth:` block | `POST /auth/token` with a username and password |

Present either one as `Authorization: Bearer <credential>`. The static token is
the simpler of the two and the one to prefer for anything new. The exchange
exists because erp-manager — and four other ERP integrations that share its
credential fields — authenticate with a username and password and cannot be
repointed at a static token without changing all five.

Rate limiting (25 rps per IP, burst 50) runs **before** authentication, on
`/auth/token` as well as on the data routes.

## The static bearer token

32 random bytes from `crypto/rand`, hex encoded, generated by the GUI's
**Generate key** button or by `cutover-seed`. Compared with
`crypto/subtle.ConstantTimeCompare`. Never logged. Rotate it by editing
`config.yaml` and restarting the service — there is no rotation window, so the
caller must be updated at the same time.

## The credential exchange

```yaml
auth:
    enabled: true
    username: bfl-reads          # operator-set
    password: 9e4xT-GSErdet…     # operator-set, generate it
    secret: 8230e0e45981…        # per-install, generated on first run
    tokenTTL: 30m                # optional; default 30m
```

Off by default. When `enabled` is false the route does not exist — `POST
/auth/token` returns `404` — and only the static token authenticates.

**Request**

```http
POST /auth/token
Content-Type: application/json

{"username":"bfl-reads","password":"9e4xT-GSErdet…"}
```

**Response** — always `200`, never `201`:

```json
{"access_token":"eyJhbGciOiJIUzI1NiIs…","token_type":"Bearer","expires_in":1800}
```

Anything wrong — bad username, bad password, missing field, unparseable body —
is a flat `401 INVALID_CREDENTIALS`. So is presenting an expired, forged or
malformed token to a data route. Never `403`: callers branch on `401` to
re-authenticate, and any other status leaves a cached credential broken until a
human clears it. (The one non-401 failure is `500 TOKEN_ISSUE_FAILED`, if HMAC
signing itself fails. It has no known trigger; it is there so a would-be
impossible error is not reported as a credential problem.)

The token is a hand-rolled HS256 JWT (`internal/auth`) carrying `sub`, `iat` and
`exp` and nothing else. There are no claims to authorise on — an issued token
grants exactly what the static token grants.

### The signing secret

32 random bytes, unique to the installation, generated on first start and saved
to `config.yaml`. It has **no default and never will**: a constant compiled into
the binary would let anyone with a copy of the source mint tokens accepted by
every deployment. That is precisely what the Node app this replaced did, along
with shipping a fixed `digitrade`/`123456` — both are rejected here, and a test
pins that.

Regenerating the secret (GUI → **Regenerate**) invalidates every token already
issued. Callers recover on their own by re-authenticating after the `401`, so it
is safe to do — but it is not silent, and a caller that caches a token past its
expiry will make one failed request first.

### Token lifetime

`tokenTTL` is a Go duration (`30m`, `1h`). Blank means 30 minutes. A malformed
value falls back to the default rather than failing startup — a typo must not
take a running installation offline — but the GUI refuses to save one, because
there the operator is still in front of the field.

Note that a caller may cache the token past its expiry and only re-authenticate
when a request is rejected. The TTL bounds how long a leaked token is useful; it
does not control refresh timing.

## Setting it up

**GUI** — tick *Enabled* under **Credential exchange (POST /auth/token)**, set a
username, press **Generate** for the password, save. The signing secret is
generated by the service on its next start.

**Headless** —

```
cutover-seed.exe -auth-user bfl-reads
```

which generates the password and the secret and prints the credentials to hand
to the calling backend. Add `-auth-password` to set one yourself, `-auth-ttl` to
override the lifetime.

Either way the connector refuses to start, and the GUI refuses to save, if
`enabled` is true with a blank username or password. A half-configured block
that quietly accepted blanks would be worse than no exchange at all.

## Rollout order

Credentials must reach the caller **before** the connector starts requiring
them:

1. Generate the username and password on the connector; do not save yet.
2. Send them to the backend operator out of band.
3. The backend updates its stored connection rows.
4. Then save on the connector and restart the service.

Doing 4 before 3 means the backend authenticates with the old fixed credentials,
gets `401`, and its ERP screens go blank until step 3 lands.

## Verifying

```bash
BASE=http://127.0.0.1:8082
# 1. exchange → 200 with access_token
curl -s -X POST -H 'Content-Type: application/json' \
     -d '{"username":"bfl-reads","password":"…"}' $BASE/auth/token
# 2. the shipped defaults must fail → 401
curl -s -o /dev/null -w '%{http_code}\n' -X POST -H 'Content-Type: application/json' \
     -d '{"username":"digitrade","password":"123456"}' $BASE/auth/token
# 3. a data route with the issued token → 200
curl -s -H "Authorization: Bearer $ISSUED" $BASE/api/custom_sql
# 4. the same with the static token → 200 (dual acceptance)
curl -s -H "Authorization: Bearer $BEARER" $BASE/api/custom_sql
# 5. anything else → 401
curl -s -o /dev/null -w '%{http_code}\n' -H 'Authorization: Bearer wrong' $BASE/api/custom_sql
```

On Windows PowerShell 5.1, put the JSON in a file and use
`--data-binary "@body.json"`: PowerShell strips the double quotes out of an
inline `-d` argument, and every request comes back `401` for a reason that has
nothing to do with the credentials.

`GET /api/ping` is the cheapest check that the service is up and a credential is
good — it is authenticated and rate-limited like everything else but touches no
database, so it stays `200` while SQL Server is down. Use `/api/health` when you
want the database checked too.

## Where it lives

| File | What |
|---|---|
| `internal/auth/token.go` | HS256 sign/verify, secret and password generation |
| `internal/api/handlers/auth.go` | `POST /auth/token`, `GET /api/ping` |
| `internal/api/middleware/auth.go` | dual acceptance, constant-time compare |
| `internal/config/model.go` | `AuthConfig`, `Validate`, `TTL` |
| `cmd/digi-erp-connectord/app.go` | first-run secret generation |
| `internal/api/auth_exchange_test.go` | the contract, pinned |
